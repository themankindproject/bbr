## 1. Reproduced defects (diff engine)

These are the highest-confidence findings because they were executed. Full
output: `docs/audit/2026-10-21-diff-probe-output.txt`.

### D1. A deleted line starting with `-- ` is parsed as a file header — Reproduced

`src/diff/parser.rs:264-268` checks `line.starts_with("--- ")` **before** the
hunk-content branch. A deletion of a SQL/Lua/Haskell comment arrives as
`--- comment` (the diff marker `-` plus content `-- comment`), so it is consumed
as a `---` header rather than a deletion.

Probe 1 input: deletion of `-- old sql comment` in `q.sql`. Observed:

```
file status=Modified old="old sql comment" new="q.sql" binary=false hunks=1 +1 -0
  hunk[0] lines=2
    Context ... content="SELECT 1;"
    Addition ... content="SELECT 2;"
```

The deletion vanished, the file's old path was overwritten with the comment
text, and the counts report `-0`. The same applies to `+++ ` content.

### D2. A context line that looks like `@@ … @@` splits the hunk — Reproduced

`src/diff/parser.rs:297` calls `parse_hunk_header` for every line before the
content-line check, and `parse_hunk_header` trims leading whitespace
(`parser.rs:350-356`). A context line whose text is `@@ -9,9 +9,9 @@` is
therefore promoted to a new hunk.

Probe 2 observed **2 hunks** where there is one; line numbers after the fake
header are wrong.

### D3. Unquoted paths lose a real `b/` directory component — Reproduced

`src/diff/parser.rs:92-99`: after locating `" b/"`, the code slices `idx + 3`
and then strips `"b/"` again. For `diff --git a/x b/b/y` the observed result is
`new="y"`; the correct path is `b/y`.

### D4. An empty added file is classified `binary` — Reproduced

`src/diff/parser.rs:704-711` treats any file with no hunks and no line counts
as binary. The heuristic is deliberate — Bitbucket omits the
`Binary files ... differ` marker, and the renderer's test suite asserts it
(`diff/renderer.rs:2843-2862`). It is nevertheless a false positive for an
**empty added text file** and for **mode-only changes** (`chmod +x`), because
neither has hunks or line counts.

Probe 4 observed `status=Added binary=true hunks=0 +0 -0`.

### D5. `--file N` followed by a pathspec always yields an empty diff — Reproduced

`src/commands/pr.rs:1091-1113` rebuilds the selected subset with
`render_raw_from_files` (`src/diff/mod.rs:107-141`), which emits `---`/`+++`
but **no `diff --git` header**. `filter_raw_diff`
(`src/diff/parser.rs:208-226`) only turns `keep` on when it sees
`diff --git `, so every line is dropped.

Probe 5 observed:

```
selected=1 rebuilt_has_diff_git=false filtered_bytes=0 filtered_has_bar=false
```

Exit status is 0 and `--json` reports zero files. `--raw` prints nothing.

### D6. `--context usize::MAX` panics — Reproduced

`src/diff/renderer.rs:2040-2042` computes `idx + 1 + context_lines` with
unchecked arithmetic. Probe 6:

```
panicked at src/diff/renderer.rs:2041:19: attempt to add with overflow
OBSERVED panic=true
```

`--context` is a `usize` accepted without an upper bound, so a user value (or a
script) aborts the process. Release builds wrap and render the wrong window.

### D7. A hostile hunk header overflows the line counter — Reproduced

`src/diff/parser.rs:440-458` increments `old_lineno`/`new_lineno` (both `u32`)
without checked arithmetic. A header such as
`@@ -4294967295,1 +0,0 @@` plus one body line panics in debug:

```
panicked at src/diff/parser.rs:455:17: attempt to add with overflow
OBSERVED panic=true
```

Release builds wrap line numbers silently.

### D8. Invalid `--file` selectors are silently ignored — Reproduced

`src/diff/mod.rs:46-78` drops tokens that parse as 0 or as an inverted range;
`select_files` (`:80-83`) treats an empty selector list as “select everything”.
Probe 8: `--file 0` → `selectors=0 selected=1` (whole diff shown), exit 0.
A typo widens the output instead of erroring.

## 2. High-confidence functional defects

### A1. `pr merge-check` derives approvals from `reviewers`, not `participants` — Spec-confirmed

`src/commands/pr.rs:683-700` builds `approvals`, `pending_reviewers`, and
`changes_requested` from `pr.reviewers`. The OpenAPI schema defines
`reviewers` items as `account` (no `approved`/`state`); only `participants`
items have those fields. `get_pr` requests the non-existent
`reviewers.approved`/`reviewers.state` fields (`src/api/pr.rs:475-486`).

Consequences: `approvals` is always empty, every requested reviewer is
“pending”, and `changes_requested` is always empty. `can_merge`
(`pr.rs:743-756`) can therefore be `true` with zero approvals and an active
changes request. `batch` (`commands/batch.rs:90-101`) and `dashboard`
(`commands/dashboard.rs:178`) already use `participants` correctly.

Status: verified against the published schema, not against a live account.

### A2. `batch cleanup-merged-branches` can never select a branch — Spec-confirmed

`src/api/repo.rs:50-59` declares `Branch.merged`, but the API's `branch`/`ref`
schemas contain no `merged` property, and `list_branches`
(`src/api/repo.rs:109-121`) requests no `fields` that would add one. The
default is `false`, so `batch.rs:511` (`if branch.merged`) is never true and
the command always reports “No merged branches found” (exit 0). It is a silent
no-op.

This is distinct from the documented “cleanup may skip unmerged local
branches” limitation: nothing is ever selected in the first place.

### A3. Deployment trigger/history use a path absent from the published API — Unverified/at risk

`src/api/deploy.rs:217-234` posts to
`/repositories/{ws}/{slug}/deployments_config/environments/{env}/changes`;
`src/api/deploy.rs:256-271` reads history from the same path. The published
Bitbucket Cloud OpenAPI document contains:

- `POST /repositories/{workspace}/{repo_slug}/environments/{environment_uuid}/changes`
  — documented as **“Update an environment”**, no request body, 202;
- `deployments_config/environments/{environment_uuid}/variables` (variables only);
- `GET /repositories/{workspace}/{repo_slug}/deployments` (global list).

No `deployments_config/.../changes` path exists in the spec. If the private
endpoint used by bbr is withdrawn or differs by deployment type, `deploy
trigger` and `deploy rollback` fail at the first request. (`deploy view
--wait` uses the documented `GET /deployments/{uuid}` and is unaffected.)
This could not be exercised without a live Bitbucket account, so it is flagged
as at-risk rather than proven broken.

### A4. `ci list` attaches steps to the wrong pipelines — Code-traced

`src/commands/ci.rs:133-160`: step futures are collected with
`buffer_unordered(5)`, which yields in **completion order**, then zipped
positionally with `pipelines`. Each future carries no pipeline identity.
Terminal pipelines return `Ok(Vec::new())` immediately, so they complete first
and shift every subsequent steps vector. `--json` and the table can show
pipeline A with pipeline B's steps.

### A5. `pr list --state all` does not request all states — Spec-confirmed

`PrState::All.as_query()` returns `None` (`src/api/pr.rs:30-39`), so no `state`
filter is added (`api/pr.rs:380-383,419-423`). Atlassian documents that the
pull-request collection returns **only open PRs by default**. Merged and
declined history is silently omitted while the command labels the result
`"all"` (`commands/pr.rs:1317-1323`).

### A6. Updating a secured variable downgrades it to plaintext — Code-traced

`src/commands/ci_vars.rs:85-101` passes the boolean `--secured` flag (default
`false`) into the PUT body; `src/api/pipeline.rs:482-495` always serializes
`secured`. Likewise `src/commands/deploy.rs:217-247` →
`src/api/deploy.rs:190-203`.

`bbr ci vars set DB_PASSWORD --value new` therefore rewrites an existing
secured variable as `secured: false` unless the caller remembers `--secured`.
The same applies to environment variables.

### A7. Config and credential writes drop unknown keys — Code-traced

`CredentialsFile` models only `[default]` (`src/config.rs:44-51`); `ConfigFile`
models only `active_context`, `contexts`, and `ui` (`src/config.rs:236-249`).
`save_config`/`save_credentials` serialize those structs wholesale
(`src/config.rs:250-262, 300-330`). Any other key in either file is deleted by
`context create/use/delete`, `config set`, and `auth setup`. Multi-profile
credentials or forward-compatible settings cannot survive a single bbr write.

### A8. `batch merge-approved --max` truncates before eligibility is known — Code-traced

`src/commands/batch.rs:168-183` uses `--max` as the **fetch** limit
(`fetch_limit = max.unwrap_or(100)`) before filtering for approvals. Approved
PRs older than the newest `--max` open PRs are never seen. The later “capped
to --max” note (`batch.rs:208-220`) is unreachable because the plan is already
at most `max`. `--max` should bound actions, not the candidate pool.

### A9. `pr diffstat` reads only the first page — Spec-confirmed

`src/api/pr.rs:720-729` performs one `send()` and returns the raw `Value`.
The API redirects to `/diffstat/{spec}`, whose response schema is
`paginated_diffstats`. Consumers `commands/pr.rs:1173-1197` and
`commands/status.rs:538-554` therefore show wrong file counts and +/− totals
for larger PRs. (Also listed as a follow-up in `docs/production-readiness.md`.)

### A10. Conflict-check errors become “No conflicts”, and the watch cache never expires — Code-traced

`src/commands/status.rs:240-248` turns the conflict result into
`matches!(&conflicts, Ok(c) if !c.is_empty())`; an `Err` becomes `false` and is
cached as a definite `Some(false)` (`:256-298`). The renderer prints
“No conflicts” for both `Some(false)` and `None`
(`status.rs:965-968`).

The per-PR cache (`:221-264`) is only consulted and inserted into; it is never
invalidated or refreshed, so `status --watch` keeps reporting the first tick's
conflict/diffstat state for the whole session. Separately, `refresh_head()`
errors are discarded (`status.rs:339`), so a branch switch can be missed.

### A11. `ci watch --json --logs` emits no logs at all — Code-traced

`CiWatchOut` has a `failure_log` field (`src/commands/ci.rs:54-66`), but it is
only populated when `!include_logs` (`ci.rs:569`). In JSON mode the `emit`
closure is a no-op (`ci.rs:296-300`), so live log lines are discarded. The
ranged log requests are still made. A machine consumer asking for `--json
--logs` receives a summary with neither live logs nor a failure excerpt.

### A12. `pr dashboard --repos` cannot raise the scan cap, and cache ignores the filter — Code-traced

`src/commands/dashboard.rs:89-120`: repositories are loaded from a cache keyed
only by workspace (`:42-48`) before `--repos` is considered; the scan is then
hard-capped at 15 (`:112-118`) with a note that says “use --repos to raise the
fetch cap”, but `--repos` only changes the initial fetch (default 200), never
the 15-repo scan. Per-repo errors are swallowed with `unwrap_or_default()`
(`:149-158`), so missing repos look like “no PRs”. The note is printed through
`spinner.println`, which is dropped when the spinner is hidden (piped stderr /
`--quiet`), so non-interactive runs see neither the cap nor the truncation.

### A13. `pr checkout` ignores the PR's source repository — Code-traced

`src/commands/pr.rs:985-1006` reads only `pr.source.branch.name` and then runs
`git fetch origin <branch>` / `git checkout <branch>`. For a PR from a fork,
origin usually has no such branch (or a different one with the same name), so
the command either fails or checks out the wrong code. The response already
contains `source.repository.full_name` (`api/pr.rs:479`).

### A14. `ci schedules create --pipeline <name>` sends an invalid selector — Spec-confirmed

`src/api/pipeline.rs:505-535` puts the pipeline name in `selector.type`
(valid enum: `branches`, `tags`, `bookmarks`, `default`, `custom`) and also in
`selector.pattern`. The correct form for a named pipeline is
`type: "custom", pattern: "<name>"`. Creation fails (or creates the default
branch pipeline) for every named pipeline. Additionally, `enabled=false`
creates the schedule enabled and then PUTs it off (`commands/ci_schedules.rs`),
leaving a live schedule if the second call fails.

### A15. `deploy rollback` can re-deploy the wrong history entry — Code-traced

`src/commands/deploy.rs:513-536` defaults to `history[1]` with no
`sort=` parameter and no state filter. `api/deploy.rs:256-271` claims
“most recent first” in a comment but does not request ordering. The API does
not document an order for the collection. A failed/stopped deployment, or the
wrong end of the list, can be selected and re-deployed.

### A16. Fetch errors are presented as clean/empty results — Code-traced

- `repo audit`: branch-restriction and default-reviewer failures become empty
  vectors (`commands/audit.rs:70-82`), so a 403/5xx is reported as “no
  restrictions configured” (an error-level audit finding) with exit 0.
- `repo permissions`: both permission lists are `unwrap_or_default()`
  (`commands/repo.rs:355-367`), so a failed fetch prints an empty table.
- `pr stack list`: any `get_pr` error becomes state `"UNKNOWN"` with exit 0
  (`commands/stack.rs:228-238`).
- `ci status`: step-fetch failures become an empty step list
  (`commands/ci.rs:214-217`).
These hide authorization/outage conditions from scripts that trust exit 0.

### A17. `read_secret_stdin` trims the secret value — Code-traced

`src/commands/mod.rs:234-242` reads all of stdin and returns
`buf.trim().to_string()`. This is correct for a trailing newline but also
strips intentional leading/trailing spaces and tabs from pipeline variables,
environment variables, webhook secrets, and deploy keys. The token-specific
reader (`commands/auth.rs:126-138`) has the same behavior, but tokens are
typically not space-sensitive; arbitrary values are.

## 4. Corrections to the previous (rejected) summary

- **`--json` placement across subcommands works.** Tested live:
  `target/debug/bbr pr stack list --json` returned a structured JSON error, so
  clap does propagate the global flag to the `StackAction` path. No bug.
- **Stack abort's local-delete failure is intentional and already documented.**
  `tests/stack_abort.rs:240-261` deliberately sets up an unmerged local commit,
  expects exit 1, and expects the branch and stack entry to be retained. The
  user must delete/back up the branch manually and re-run. This is consistent
  with the limitation noted in `docs/production-readiness.md`; it is a UX
  surprise (remote branch is already gone), not an unhandled bug.
- **Webhook-secret and issue-assignee clearing are not proven.** The published
  OpenAPI document has no request-body schema for those PUTs. They are
  downgraded to M23.
- **The deployment-trigger endpoint is not in the published spec**, but bbr's
  changelog claims the feature; it may be a private endpoint. It is flagged as
  at-risk (A3), not asserted broken.
- The earlier “80 source files” figure was wrong: there are **63** files under
  `src/`. The full list and line counts are in
  `docs/audit/2026-10-21-source-inventory.txt` and the ledger below.
